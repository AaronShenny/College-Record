# Recordly 0.3.0 implementation verification

## Completed locally

- Type checking for the React renderer, shared services and native-service interfaces passed.
- The complete shared-service suite passed all 80 tests. One additional conditional-write regression was added afterward and passed in a focused run; it changes Drive's ETag after the final revision check and confirms the newer index is not overwritten or acknowledged.
- All nine native service/renderer bridge tests, 12 portable Rust tests, eight archived Electron-boundary tests and 24 Python document tests passed. Word-related tests use controlled doubles, not an installed Office instance.
- Configuration tests cover exclusion of student work, optional template inclusion, pending mappings/source roles, every existing-subject/template combination, identity rewriting and malformed/oversized imports.
- Sync tests cover both explicit conflict choices, one-use stale reviews, generated/import inventories, concurrent local changes, interrupted download activation and failed publication without replacing the acknowledged graph.
- Production Tauri renderer/service assets built successfully. Source hashes and platform context were regenerated by the existing evidence script. This is not a Windows executable or NSIS build.
- The running development preview restarted cleanly and a fresh screenshot showed Recordly with no console errors. The logo/icon uses tracked local assets, not an uploaded file at runtime.
- A single browser interaction pass exercised Save Now ordering, dynamic editor controls, conflict cancellation/confirmation and Drive-winner reload, close failure/return-to-editing, and successful renderer close acknowledgment. It used explicit in-memory IPC doubles in an isolated browser context: no real Google account, native Rust host or Drive content was accessed.
- The Windows-only Rust host source was syntax-parsed. Its request fence registers active work before checking closing, so a save cannot start unnoticed between the closing check and operation registration; an RAII guard releases counts even on early failures.
- Failed bootstrap followed by close is covered in the native decision-policy tests and the real bridge failure test. The native window close path can exit without a renderer only when no service exists, all active bootstrap requests have drained and no dirty editing state exists. If a request started a service during the drain, the ordinary renderer save/Drive-acknowledged close path is required instead. Diagnostics cannot start the service later from an unmounted bootstrap-error page.

## Not certified by these checks

- Compilation/installation of the Windows-only host and installer; legacy upgrade registration, shortcuts and uninstall entries after a display-name change.
- Real Windows X/Alt-F4 closing, network failure/retry, forced termination, disk-full recovery or laptop handoff against actual Drive.
- Live Drive conditional-update response headers and account/OAuth expiry behavior.
- Index pagination and section headers in installed Word/PDF, or Word automation itself.
- Any startup/download timing target on the owner's 4 GB/HDD computer.
- Production publication or signed automatic-update readiness.

Use **WINDOWS-VERIFICATION.md** for the targeted installed-app checks. Close gating cannot upload after power loss or a forced process kill; local recovery files remain necessary. Older binaries must not be used to edit workspaces containing unfamiliar optional schema fields.
